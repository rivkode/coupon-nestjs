## 한 줄 요약

설계 시나리오(쿠폰 100장, 요청 대부분이 매진 이후 도착)에서 **993 req/s, 실패 0%, p95 61ms** 로
목표 1,000 TPS 를 만족한다. 유실 0, 초과 발급 0.

다만 재고를 크게 잡아 **모든 요청이 전 구간을 통과하게 만들면 무너진다** — server-c 의 소비 속도가
약 96 msg/s 라 백로그가 쌓이고, 보완 스케줄러의 재발행이 되먹임을 만들어 Circuit Breaker 가 열린다.

| 항목 | 값 |
|---|---|

```bash
npm run start:a & npm run start:b & npm run start:c &
TOTAL_INVENTORY=100 ./load-test/run-load.sh
```

## 결과 ① 설계 시나리오 — 통과

쿠폰 100장에 60초 동안 1,000 TPS. 요구사항이 전제하는 상황이다
(재고보다 요청이 훨씬 많아 매진이 반드시 발생하고, 대부분의 요청이 매진 이후에 도착한다).

| 지표 | 값 |
|---|---|
| 처리량 | **992.9 req/s** (59,578 건 / 60초) |
| 실패율 | **0.000%** |
| latency | avg 24.6ms · med 5.2ms · **p95 61.2ms** · max 896ms |
| 5xx | 0 |

### 정합성

| 항목 | 값 |
|---|---|
| A 접수 | 1,678 |
| A 매진 단락 | **57,900** (97.2%) |
| C 처리 | 1,678 (발급 100 + 매진 1,578) |
| 재고 잔량 | **0 / 100** |
| 미발행 outbox | 0 |
| Kafka lag | 0 |

- **A 접수 = C 처리** → 유실 없음
- **발급 정확히 100건** → 초과 발급 없음 (비관적 락 성립)
- `pending_scheduler_give_up` **0** → 30초 SLA 위반 없음 (재발행 363건은 전부 회복)

### 매진 단락이 하는 일

전체 요청의 **97.2%가 A 에서 끊긴다.** 이 요청들은 B 의 Redis 적재도, Kafka 왕복도,
C 의 비관적 락도 쓰지 않는다. latency 중앙값이 5.2ms 인 이유가 이것이다 —
대부분의 요청이 Redis `EXISTS` 한 번과 요청 로그 INSERT 한 번으로 끝난다.

설계에서 "차단 위치를 가장 이른 지점에 둔다"고 한 판단이 수치로 확인된다.

## 결과 ② 재고를 크게 잡으면 — 무너진다

재고 10,000 으로 같은 부하를 주면 매진 단락이 발화하지 않아 **모든 요청이 전 구간을 통과**한다.

| 지표 | 값 |
|---|---|
| 처리량 | 889 req/s |
| 실패율 | **64.88%** (503) |
| latency | avg 276ms · p95 861ms |
| A 접수 / C 처리 | 18,919 / 9,192 (백로그) |

503 은 **전부 `circuit-open`** 이었다.

### 원인 — 되먹임 고리

```
C 소비 속도(96/s) < 유입(315/s)
      ↓
Kafka 백로그 누적
      ↓
결과가 10초 안에 안 돌아옴 → B 스케줄러가 재발행 (4,095회)
      ↓
스케줄러가 B 의 이벤트 루프를 점유 (C 로의 HTTP 조회 + Redis + 재발행)
      ↓
B 응답 지연 → A 의 slow-call 임계(800ms) 초과
      ↓
Circuit Breaker OPEN → 이후 요청 전부 503
```

### 구간별로 끊어 측정한 결과

| 구간 | 측정값 | 판정 |
|---|---|---|
| **server-b 단독** (A·CB 배제, 스케줄러 비활성) | **999.8 req/s, 실패 0%, p95 73ms** | 병목 아님 |
| **server-c 소비** (메시지 5,000건 드레인) | **96 msg/s** | **병목** |

server-b 는 1,000 TPS 를 혼자서 깔끔하게 소화한다. 병목은 server-c 의 소비 속도다.

### C 가 느린 이유 — 커밋 주기는 아니다

레코드마다 Kafka 커밋하는 것(`autoCommitThreshold: 1` = ack-mode RECORD)이 원인일 것으로 보고
커밋 주기를 10으로 바꿔 재측정했으나 **97 msg/s 로 차이가 없었다.**

남는 설명은 **레코드당 MySQL 왕복 횟수**다. 한 건의 발급 트랜잭션은
중복 체크 → 이벤트 조회 → 재고 `FOR UPDATE` → 재고 UPDATE → `user_coupon` INSERT →
`outbox_event` INSERT → COMMIT, 그리고 커밋 후 재고 fresh read 까지 **왕복 8회 이상**이다.
96/s ≈ 레코드당 10ms 이므로 왕복당 약 1ms — Docker MySQL 왕복 지연과 맞아떨어진다.

즉 CPU 가 아니라 **왕복 지연에 묶여 있다.** `partitionsConsumedConcurrently: 1` 이라
파티션을 하나씩 순차 처리하는 것도 여기에 곱해진다.

## 해석

두 결과는 모순이 아니다. **설계가 의도한 것이 정확히 그것**이다.

- 사용자 응답 경로(A→B)와 발급 처리(C)를 분리했기 때문에, C 가 느려도 사용자는 빠른 응답을 받는다
- 매진이 빨리 발생하면 대부분의 요청이 A 에서 끊겨 C 로 가는 부하 자체가 작아진다
- 재고가 크면 C 로 가는 부하가 계속 유지되고, 이때 C 의 소비 속도가 시스템 상한이 된다

따라서 **"C 로 지속 유입되는 양이 C 의 소비 속도를 넘지 않아야 한다"** 가 운영 조건이다.
지금 수치로는 약 96 msg/s 다.

## 남은 과제

| 과제 | 내용 |
|---|---|
| 1 vCPU 재측정 | 컨테이너 CPU 제한을 걸고 목표 사양에서 다시 측정 |
| C 처리량 개선 | 왕복 축소(재고 차감을 조건부 UPDATE 한 문장으로), 파티션 동시성 상향 검토. 둘 다 락 전략에 영향을 주므로 별도 판단 필요 |
| 되먹임 차단 | 백로그가 클 때 스케줄러가 재발행을 억제하도록(lag 인지) 할지 검토 |
| 미이관 설정 재검토 | `linger.ms`, `batch.size`, 풀 대기 상한 등이 처리량에 주는 영향 측정 |

## 실행 방법

```bash
# 인프라 + 세 서버 기동 후
SCENARIO=smoke TOTAL_INVENTORY=100 ./load-test/run-load.sh   # 스모크
TOTAL_INVENTORY=100 ./load-test/run-load.sh                  # 1,000 TPS × 60초
RATE=1000 k6 run load-test/scenarios/server-b-direct.js      # B 단독 상한
```

`run-load.sh` 는 시드 → Redis 초기화 → k6 실행 → **A 접수 vs C 처리 대조**까지 수행하고,
유실이나 초과 발급이 있으면 실패로 종료한다.
